# M5.6d — Combat: the Defending Player — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make "who is being attacked" a real turn-based action instead of the head of a list. `Pawl.Type.Combat` gains one field, `defender :: Maybe PlayerId`; `Combat.chooseDefender` fills it at the beginning of combat step (CR 507.1, CR 703.4h) from `Combat.attackableOpponents`, asking `Prompt.ChooseDefender` when there is more than one candidate and not asking when there is one; `declareAttackers` and `declareBlockers` read the field; `Combat.defendingPlayers` is deleted. The proof is Palace Jailer: alice attacks the monarch and takes the crown, or attacks the other opponent and does not, with every input the same but the answer to one prompt.

**Architecture:** Today `Combat.defendingPlayers` is a single function serving two incompatible jobs — it is read as *the* defender by `declareAttackers` (`defender : _`, dropping the tail) and as *all* defenders by `declareBlockers` (a `forM_` over the whole list). Those two jobs come apart the moment the list can have two entries. The split is: `Combat.attackableOpponents` answers "who *could* be attacked" (the candidate set, read only by `chooseDefender`), and the new `Combat.defender` field answers "who *is* being attacked" (read by `declareAttackers` and `declareBlockers`). Between them sits one new turn-based action, wired into `Engine.runTurnBasedActions` at `Phase.Combat CombatStep.BeginningOfCombat` — a step that previously fell through to `_ -> pure ()`. Nothing else moves: `Pawl.Damage` already reads each attacker's own `AttackTarget`, so combat damage needs no change at all, and `AttackTarget` stays a `newtype` because CR 508.1b's per-creature announcement still has no trigger in this pool.

The field is `Maybe`, not a bare `PlayerId`, because there is a real state before the choice is made and after CR 511 clears combat, and because a turn with no active player (CR 800.4j) never makes the choice at all — `Nothing` then means no attack is possible, which is the correct outcome rather than a fallback.

**Tech Stack:** GHC 9.14.1 from the Nix flake; Haskell 2010 with no new language extensions; `tasty` + `tasty-hunit` for tests; `ormolu`/`hlint`/`cabal-gild` via `hooky`.

### Two places the spec's claim did not survive the check, and what to write instead

1. **CR 511.3 does not reset the defending player.** §3.6's draft field comment says `Nothing` holds `after CR 511.3's end-of-combat reset`. CR 511.3 removes creatures, battles and planeswalkers from combat; it says nothing about the defending-player designation, and CR 506.4's removal list is likewise about permanents. What actually scopes the designation is **CR 506.2**, whose sentences all begin *During the combat phase* — the designation cannot outlive the phase — together with CR 703.4h and CR 507.1 making the choice a *per-beginning-of-combat-step* action, so a turn with two combat phases (CR 506.7c) chooses twice. Write the field's comment from CR 506.2 + CR 703.4h and cite CR 511.3 only for what it actually does. `Combat.clearCombat` is still the function that performs the reset, exactly as today, and its own comment keeps its CR 511.3 citation for the attacker/blocker half.
2. **CR 506.2a does not literally say the candidates are the still-playing players minus the active player.** It says the attacking player chooses one of their **opponents**. Three rules get from there to a list: CR 102.1 (a player is one of the people **in the game**, so someone who has left is not a player and cannot be an opponent), CR 806.1 (in a free-for-all the players compete as individuals, so every other player is an opponent), and CR 102.3 (the one reading this is wrong for — a teammate is not an opponent — which pawl has no teams to express; #175). Write `attackableOpponents`'s comment from those three, not from CR 506.2a alone. This is the same argument `Count.playersFor` and `Filter.matches` already carry for the `Opponent` axis, and phrasing it identically is deliberate.

- Consumes: `Departure.stillPlayingInOrder :: GameState -> [PlayerId]` (`source/library/Pawl/Departure.hs:49`), already imported by `Pawl.Combat`.

**`Combat.defendingPlayers` is deliberately NOT deleted here.** Its two callers switch in Task 4, and deleting it earlier would force those two changes into this commit. Until then the two functions coexist and `attackableOpponents` has no library caller — which produces no warning, because the project has no export lists and everything is exported.

**Why `stillPlayingInOrder` and not `stillPlaying`:** `Departure.stillPlaying` reads the players map and therefore comes back in `PlayerId` order, which is an implementation artifact. `GameState.turnOrder` is the permanent seating roster (M5.6a, §3.1), and seating order is the game's own ordering for anything player-shaped — it is what makes "the first candidate" mean the next seat rather than the lowest id. The two agree on every fixture whose seating is ascending, so Step 1's rotated-seating assertion is what makes the choice observable rather than a matter of taste.
